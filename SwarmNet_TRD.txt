1. SYSTEM ARCHITECTURE

SwarmNet uses a fully decentralized peer-to-peer architecture. There is no
central broker or coordinator. Each drone is a self-contained process.

PROCESS MODEL
  - N drone processes run on localhost, each bound to a unique port.
  - One optional Visualizer process (Pygame) subscribes to all drone state
    broadcasts and renders the 2D view.
  - One optional Dashboard process (Flask) aggregates metrics and serves the
    web UI.

COMMUNICATION TOPOLOGY
  - Each drone maintains PUSH/PULL sockets to all peers (full mesh for N<=20).
  - Leader uses a broadcast channel to announce log entries and waypoints.
  - Gossip uses random peer selection — not a fixed topology.

PROCESS ROLES
  DroneNode      Core process. Runs Raft state machine, gossip agent,
                 flocking compute, and task handler. One per simulated drone.

  Visualizer     Subscriber process. Receives state from all DroneNodes via
                 ZeroMQ PUB/SUB. Renders Pygame window. Read-only.

  Dashboard      Flask app. Polls DroneNode HTTP endpoints (or subscribes via
                 ZeroMQ) for metrics. Serves web UI at localhost:5000.

  Launcher       Shell script or Python script that spawns all DroneNode
                 processes with correct arguments.

4. ALGORITHM SPECIFICATIONS

4.1 RAFT CONSENSUS


STATES
  Each DroneNode is in exactly one state at any time:
    FOLLOWER    Default state. Receives heartbeats from leader.
    CANDIDATE   Election timeout fired. Requesting votes from peers.
    LEADER      Won election. Sends heartbeats. Replicates log.

TERMS
  Each election starts a new integer term (monotonically increasing).
  Nodes reject messages from lower terms.
  Nodes update their term and revert to FOLLOWER on seeing a higher term.

ELECTION TIMEOUT
  Each follower picks a random timeout T in [ELECTION_TIMEOUT_MIN,
  ELECTION_TIMEOUT_MAX] (default: 150 ms – 300 ms).
  If no heartbeat received within T, the follower starts an election.

ELECTION PROCESS
  1. Increment currentTerm.
  2. Transition to CANDIDATE.
  3. Vote for self.
  4. Send VoteRequest(term, candidateId, lastLogIndex, lastLogTerm)
     to all peers.
  5. If votes received >= floor(N/2)+1: become LEADER.
  6. If heartbeat received from valid leader: revert to FOLLOWER.
  7. If election timeout fires again: start new election (increment term).

LEADER OPERATION
  1. Send Heartbeat(term, leaderId, leaderCommit) to all followers
     every HEARTBEAT_INTERVAL ms (default: 100 ms).
  2. On new command: append to local log, send AppendEntries RPC to
     all followers.
  3. Once majority acknowledge: commit entry, apply to state machine,
     respond to client.

LOG ENTRY STRUCTURE
  {
    "index"    : <int>,        sequential log index
    "term"     : <int>,        term when entry was created
    "command"  : <string>,     e.g. "MOVE 120 340" or "ASSIGN TASK_A DRONE_3"
    "committed": <bool>
  }

RAFT CONSTANTS (config.ini)
  HEARTBEAT_INTERVAL     = 100    (ms)
  ELECTION_TIMEOUT_MIN   = 150    (ms)
  ELECTION_TIMEOUT_MAX   = 300    (ms)
  RPC_TIMEOUT            = 50     (ms)


4.2 GOSSIP PROTOCOL

PURPOSE
  Disseminate each drone's local state to the entire swarm without
  flooding. Achieves eventual consistency in O(log N) rounds.

STATE TABLE ENTRY (per drone)
  {
    "drone_id"   : <int>,
    "x"          : <float>,
    "y"          : <float>,
    "vx"         : <float>,
    "vy"         : <float>,
    "battery"    : <float>,        0.0 – 100.0
    "task"       : <string>,
    "raft_state" : <string>,       "leader" | "follower" | "candidate"
    "term"       : <int>,
    "timestamp"  : <float>         Unix epoch (float)
  }

GOSSIP CYCLE (every GOSSIP_INTERVAL ms, default 200 ms)
  1. Select GOSSIP_FANOUT (default 2) random peers.
  2. Send own state table (all known entries) to each selected peer.
  3. On receive: merge incoming table with local table.
     Merge rule: keep entry with the highest timestamp per drone_id.

CONVERGENCE MEASUREMENT
  Round R is complete when all alive nodes have an entry for every
  other alive node with timestamp >= round start time.
  Log round count per gossip cycle to metrics collector.

GOSSIP CONSTANTS
  GOSSIP_INTERVAL    = 200     (ms)
  GOSSIP_FANOUT      = 2       (peers per round)


4.3 REYNOLDS FLOCKING

Each drone computes a new velocity vector every FLOCKING_TICK ms
(default: 50 ms) using three weighted steering forces.

INPUT
  - Own position (x, y) and velocity (vx, vy)
  - Neighbor list from gossip state table filtered by NEIGHBOR_RADIUS

RULE 1 — SEPARATION (weight: W_SEP, default 1.5)
  For each neighbor closer than MIN_SEP_DIST (default 30 units):
    Add a vector pointing away from that neighbor, scaled inversely
    by distance.
  separation_force = normalize(sum of away-vectors) * W_SEP

RULE 2 — ALIGNMENT (weight: W_ALI, default 1.0)
  Compute average velocity of all neighbors within NEIGHBOR_RADIUS.
  alignment_force = normalize(avg_velocity - own_velocity) * W_ALI

RULE 3 — COHESION (weight: W_COH, default 1.0)
  Compute center of mass of all neighbors within NEIGHBOR_RADIUS.
  cohesion_force = normalize(center_of_mass - own_position) * W_COH

WAYPOINT STEERING (weight: W_WAY, default 2.0)
  Leader broadcasts current target waypoint via Raft log.
  Each drone adds a force toward its formation target position
  (offset from waypoint based on drone_id for formation shape).
  waypoint_force = normalize(target - own_position) * W_WAY

VELOCITY UPDATE
  new_velocity = own_velocity
               + separation_force
               + alignment_force
               + cohesion_force
               + waypoint_force
  new_velocity = clip(new_velocity, MAX_SPEED)   (default MAX_SPEED = 5.0)
  new_position = own_position + new_velocity * dt

FLOCKING CONSTANTS
  NEIGHBOR_RADIUS    = 100.0    (simulation units)
  MIN_SEP_DIST       = 30.0     (simulation units)
  MAX_SPEED          = 5.0      (units per tick)
  W_SEP              = 1.5
  W_ALI              = 1.0
  W_COH              = 1.0
  W_WAY              = 2.0
  FLOCKING_TICK      = 50       (ms)


4.4 CONTRACT NET TASK ALLOCATION

PURPOSE
  Distribute tasks among drones via a distributed auction without a
  central task manager (leader facilitates, but any drone can bid).

PROCESS
  1. Leader posts task announcement via Raft log:
       ANNOUNCE task_id description deadline
  2. All drones compute a bid score:
       bid = (battery_level * 0.5) + (1 / distance_to_task * 0.5)
  3. Drones send bid to leader within BID_WINDOW ms (default 500 ms).
  4. Leader awards task to highest bidder via Raft log entry:
       AWARD task_id drone_id
  5. Winning drone sends confirmation.
  6. Task status transitions: OPEN → AWARDED → IN_PROGRESS → DONE.

TASK STATES
  OPEN          Announced, bids being collected
  AWARDED       Winner selected, awaiting confirmation
  IN_PROGRESS   Drone executing task
  DONE          Task completed
  FAILED        Drone died mid-task; leader re-announces


5. COMMUNICATION DESIGN

ZMQEROMQ SOCKET TYPES USED

  Pattern           Socket Pair         Usage

  PUSH / PULL       PUSH → PULL         Unicast RPC (vote requests, heartbeats,
                                        AppendEntries)
  PUB / SUB         PUB → SUB           Broadcast (state for visualizer,
                                        leader announcements)
  REQ / REP         REQ → REP           Synchronous calls (only for metrics
                                        polling from dashboard)

PORT ASSIGNMENT
  Base port defined in config.ini (default: 5600).
  Drone i listens on:
    PULL socket:  BASE_PORT + i           (e.g., drone 0 → 5600)
    PUB socket:   BASE_PORT + 100 + i     (e.g., drone 0 → 5700)
  Visualizer subscribes to PUB sockets of all drones.
  Dashboard polls REP sockets: BASE_PORT + 200 + i

MESSAGE FORMAT (JSON over ZeroMQ frame)
  All messages are UTF-8 encoded JSON strings.

  VOTE REQUEST
  {
    "type"          : "vote_request",
    "term"          : <int>,
    "candidate_id"  : <int>,
    "last_log_index": <int>,
    "last_log_term" : <int>
  }

  VOTE RESPONSE
  {
    "type"          : "vote_response",
    "term"          : <int>,
    "vote_granted"  : <bool>,
    "voter_id"      : <int>
  }

  HEARTBEAT / APPEND ENTRIES
  {
    "type"          : "append_entries",
    "term"          : <int>,
    "leader_id"     : <int>,
    "prev_log_index": <int>,
    "prev_log_term" : <int>,
    "entries"       : [ <log_entry>, ... ],
    "leader_commit" : <int>
  }

  APPEND ENTRIES RESPONSE
  {
    "type"          : "append_entries_response",
    "term"          : <int>,
    "success"       : <bool>,
    "follower_id"   : <int>,
    "match_index"   : <int>
  }

  GOSSIP PUSH
  {
    "type"          : "gossip",
    "sender_id"     : <int>,
    "state_table"   : { "<drone_id>": <state_entry>, ... }
  }

  STATE BROADCAST (PUB channel for visualizer)
  {
    "type"          : "state_broadcast",
    "drone_id"      : <int>,
    "x"             : <float>,
    "y"             : <float>,
    "vx"            : <float>,
    "vy"            : <float>,
    "raft_state"    : <string>,
    "term"          : <int>,
    "battery"       : <float>
  }

FAULT SIMULATION
  fault_sim.py wraps all send() calls.
  If PACKET_LOSS_RATE > 0.0, each message is dropped with probability p.
  Dropped messages are logged for metrics.


6. DATA STRUCTURES

DroneState (dataclass in state.py)
  drone_id       : int
  x              : float
  y              : float
  vx             : float
  vy             : float
  battery        : float          starts at 100.0, decrements 0.1/s
  raft_state     : str            "leader" | "follower" | "candidate"
  current_term   : int            starts at 0
  voted_for      : int | None     candidate_id voted for in current term
  log            : list[dict]     list of log entry dicts
  commit_index   : int            highest log index known to be committed
  last_applied   : int            highest log index applied to state machine
  next_index     : dict[int,int]  leader only: next log index to send per peer
  match_index    : dict[int,int]  leader only: highest index replicated per peer
  task           : str | None
  alive          : bool

RaftLog (in log.py)
  entries        : list[LogEntry]
  LogEntry fields: index, term, command, committed

GossipTable (in state_table.py)
  table          : dict[int, StateTableEntry]    keyed by drone_id
  StateTableEntry: all DroneState fields + timestamp

Task (in task.py)
  task_id        : str
  description    : str
  status         : TaskStatus    Enum: OPEN/AWARDED/IN_PROGRESS/DONE/FAILED
  assigned_to    : int | None
  deadline       : float         Unix epoch

MetricsRecord (in collector.py)
  event_type     : str           "election" | "gossip" | "formation"
  timestamp      : float
  value          : float         election_ms | convergence_rounds | avg_error
  swarm_size     : int

11. PERFORMANCE BENCHMARKS

BENCHMARK 1 — ELECTION TIME vs N
  N values tested: 3, 5, 7, 10, 15, 20
  For each N: kill leader 10 times, record re-election time (ms).
  Plot: box plot of election time distribution per N.
  Expected: election time stays below 500 ms for all tested N.

BENCHMARK 2 — GOSSIP CONVERGENCE vs N
  N values tested: 5, 10, 15, 20
  For each N: measure rounds until all nodes have consistent state.
  Run 20 trials per N.
  Plot: mean convergence rounds vs N (should be ~log2(N)).

BENCHMARK 3 — FORMATION ERROR vs PACKET LOSS
  N = 10 fixed.
  Packet loss rates: 0%, 10%, 30%, 50%
  Metric: average distance of each drone from its ideal formation position.
  Measure over 60 seconds per run.
  Plot: formation error (units) vs packet loss %.

BENCHMARK 4 — MESSAGE THROUGHPUT
  N = 10.
  Measure total messages sent per second across all nodes.
  Break down by type: heartbeat, gossip, vote, state broadcast.
  Log to CSV for 30 seconds.

ALL BENCHMARKS
  Run with fixed random seed for reproducibility.
  Output to metrics/ directory as CSV.
  Generate matplotlib plots (PNG) with exporter.py.
