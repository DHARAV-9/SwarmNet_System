--------------------------------------------------------------------------------
1. PROJECT OVERVIEW
--------------------------------------------------------------------------------

SwarmNet is a fully software-simulated autonomous drone swarm system built
on top of Distributed Consensus Algorithms. The system models N drones as
independent Python processes that communicate over ZeroMQ sockets, elect a
leader via the Raft consensus algorithm, synchronize world state using a
Gossip protocol, and exhibit emergent flocking behavior through Reynolds'
three-rule algorithm.

The project runs entirely on a single laptop — no physical drone hardware is
required. Each drone process is analogous to a real drone node: it maintains
its own state, communicates with peers, and participates in collective
decision-making without any centralized controller.

The simulation is visualized in real time using Pygame (2D positional view)
and a Flask web dashboard (node health, election terms, gossip rounds).

This project demonstrates practical application of distributed systems theory
in a robotics-inspired context, covering:
  - Consensus & fault tolerance (Raft)
  - Epidemic state propagation (Gossip protocol)
  - Emergent collective behavior (Reynolds flocking)
  - Distributed task allocation (Contract Net Protocol)


--------------------------------------------------------------------------------
2. PROBLEM STATEMENT
--------------------------------------------------------------------------------

Traditional drone swarm systems rely on a central ground station that
coordinates all drones. This creates a single point of failure — if the
controller goes down, the entire swarm fails.

Real-world scenarios (disaster relief, military, agriculture) demand swarms
that are:
  - Self-organizing: no central master needed
  - Fault-tolerant: if one or more drones fail, the swarm continues
  - Consistent: every drone agrees on the current state of the world
  - Scalable: adding more drones improves capability, not complexity

This project addresses these requirements by implementing distributed
consensus at the swarm coordination layer, turning each drone into a fully
autonomous peer node that participates in collective decision-making.

3. GOALS & OBJECTIVES
--------------------------------------------------------------------------------

PRIMARY GOALS
  G1. Implement Raft consensus algorithm for leader election and log replication
      across simulated drone nodes.

  G2. Implement Gossip protocol for decentralized state synchronization so
      every drone has an eventually-consistent view of the swarm.

  G3. Implement Reynolds flocking rules (separation, alignment, cohesion) to
      produce emergent formation behavior driven by consensus commands.

  G4. Demonstrate fault tolerance: up to floor(N/2) drone failures must not
      break swarm operation.

  G5. Provide real-time visualization and metrics for academic evaluation.

ACADEMIC OBJECTIVES
  O1. Demonstrate understanding of CAP theorem trade-offs in swarm design.
  O2. Compare Raft vs Bully election algorithm performance experimentally.
  O3. Measure and plot gossip convergence time vs swarm size.
  O4. Generate a reproducible benchmark suite for the final report.

6. FEATURES & REQUIREMENTS
--------------------------------------------------------------------------------

6.1 FUNCTIONAL REQUIREMENTS
-----------------------------

FR-01  DRONE NODE SIMULATION
  Each drone must run as an independent Python process.
  Each node must have: unique ID, (x, y) position, velocity vector,
  battery level (simulated), task status, and Raft state
  (follower / candidate / leader).

FR-02  RAFT LEADER ELECTION
  The system must elect exactly one leader at any time.
  Leader sends heartbeats every 100 ms to all followers.
  If a follower receives no heartbeat within 150–300 ms (randomized
  election timeout), it becomes a candidate and requests votes.
  A candidate with majority votes (floor(N/2)+1) becomes leader.
  On leader failure, a new election must complete within 500 ms.

FR-03  RAFT LOG REPLICATION
  The leader must maintain a replicated log of swarm commands
  (waypoint changes, task assignments, formation updates).
  Committed log entries must be replicated to a majority of nodes
  before being applied.
  Log must remain consistent after leader failure and re-election.

FR-04  GOSSIP PROTOCOL
  Each node must gossip its local state to 2 random peers every 200 ms.
  State includes: position, battery %, task, Raft term, last-seen timestamp.
  All nodes must converge to a consistent swarm state within
  O(log N) gossip rounds.

FR-05  REYNOLDS FLOCKING
  Each drone must compute its next velocity using three rules:
    - Separation: steer away from drones closer than MIN_DIST (30 units)
    - Alignment: match average velocity of neighbors within NEIGHBOR_RADIUS
    - Cohesion: steer toward center of mass of neighbors
  Weights for each rule must be configurable at runtime.
  Leader drone broadcasts target waypoint; followers flock toward it.

FR-06  FAULT INJECTION
  User must be able to kill any drone process via dashboard button or
  keyboard shortcut.
  Simulated packet loss must be injectable (10%, 30%, 50%) via config.
  Swarm must recover formation and elect new leader after fault.

FR-07  PYGAME VISUALIZATION
  A 2D top-down window must show all drone positions as colored circles.
  Leader drone must be visually distinct (different color + crown label).
  Velocity vectors must be shown as short arrows.
  Formation boundary or convex hull must be optionally overlaid.
  Window must update at minimum 30 FPS.

FR-08  FLASK DASHBOARD
  A web UI at localhost:5000 must show:
    - Current leader ID and election term number
    - Each node's status: alive / dead / candidate
    - Gossip round count and last convergence time
    - Battery levels of all nodes
    - Fault injection controls

FR-09  METRICS & EXPORT
  System must log and export to CSV:
    - Election time (ms) per election event
    - Gossip convergence rounds per cycle
    - Formation error (average distance from ideal position)
    - Message count per second per node

FR-10  TASK ALLOCATION
  Leader must be able to broadcast a task list (e.g., scan zone A, B, C).
  Drones must bid for tasks using a simple auction protocol.
  Task assignments must be replicated via Raft log.


6.2 NON-FUNCTIONAL REQUIREMENTS
---------------------------------

NFR-01  PERFORMANCE
  Leader election must complete in under 500 ms for N <= 20.
  Gossip must converge in under 5 rounds for N <= 20.
  Pygame visualization must maintain >= 30 FPS during normal operation.

NFR-02  FAULT TOLERANCE
  System must operate correctly with up to floor(N/2) simultaneous
  node failures (standard Raft quorum guarantee).
  No single drone failure should cause permanent swarm halt.

NFR-03  SCALABILITY
  Architecture must support 5 to 20 drone nodes without code changes.
  N is set via a single config parameter at startup.

NFR-04  REPRODUCIBILITY
  All random seeds must be seedable for deterministic test runs.
  Benchmark runs must produce identical results given the same seed.

NFR-05  PORTABILITY
  Must run on Windows, macOS, and Linux with Python 3.10+.
  No dependencies outside: pygame, pyzmq, flask, numpy, matplotlib.

NFR-06  TESTABILITY
  Each algorithm module (raft, gossip, flocking) must have unit tests.
  Minimum 80% line coverage on core algorithm files.

NFR-07  CODE QUALITY
  Code must follow PEP 8.
  Each module must have docstrings.
  README must include setup and run instructions.

11. RISKS
--------------------------------------------------------------------------------

  R1. ZeroMQ port conflicts on some OS
      Mitigation: Auto-assign ports from a configurable base port

  R2. Raft split-vote deadlock in small N (N=3)
      Mitigation: Randomized election timeouts (150–300 ms range)

  R3. Pygame performance drop at N > 15
      Mitigation: Cap visualization FPS independently of simulation loop

  R4. Gossip convergence slower than expected under high packet loss
      Mitigation: Increase fanout from 2 to 3 peers under stress

  R5. Examiner unfamiliar with simulation-only projects
      Mitigation: Include a clear explanation in README and report intro
      that simulation is the standard methodology in distributed systems
