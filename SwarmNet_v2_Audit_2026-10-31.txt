D. TOP FIVE RISKS
=================

Scores use likelihood × impact on a 1–5 scale.

1. Measurements falsely indicate success because targets are published as telemetry.
   Score: 5 × 5 = 25.
   Mitigation: Subscribe to actual pose, velocity, battery and connection state; compare against independent Gazebo truth.

2. Current stack cannot launch because images, ports and ROS packaging are broken.
   Score: 5 × 5 = 25.
   Mitigation: Repair a pinned one-drone configuration before attempting any swarm.

3. Scope exceeds available development time.
   Score: 5 × 5 = 25.
   Mitigation: Freeze a 5–10-drone baseline and select one research contribution.

4. N=50 exceeds practical compute budget or loses real-time behavior.
   Score: 4 × 5 = 20.

   Score: 4 × 5 = 20.

E. TECHNICAL-VALIDITY FINDINGS

1. TELEMETRY CURRENTLY FABRICATES A HEALTHY FORMATION
----------------------------------------------------

The follower's publish_state() copies the target into x/y/z, sets battery to 100, and sets alive=True.

Evidence:
  swarmnet_v2/swarmnet_ros2/swarmnet_follower/swarmnet_follower/follower_node.py:75

2. A ROS2 TOPIC NAME IS INVALID
------------------------------

/swarm/drone_state/1 has a numeric final token. ROS2 name tokens cannot start with digits. Use /swarm/drone_state/drone_1 or /drone_1/state. This affects both the PRD/TRD topic design and the follower implementation. Runtime exception text remains unverified because ROS2 could not start.

Source: ROS2 naming rules
https://design.ros2.org/articles/topic_and_service_names.html

4. DOCKER PORTS OVERLAP
----------------------

Compose lines 21–22 publish both 14550–14599 and 14540–14589. They overlap on 40 host UDP ports.

Evidence:
  swarmnet_v2/docker-compose.yml:20

Compose syntax validation does not prove those bindings can start. Define non-overlapping endpoints and separate GCS traffic from offboard/MAVROS traffic.

5. MAVLINK ROUTING IS NOT ESTABLISHED
-----------------------------------

The launcher exports MAV_SYS_ID and MAVLINK_REMOTE_PORT, but there is no checked PX4 startup script proving these environment variables are consumed. Printed configuration is not effective firmware configuration.

The MAVROS launch points at ports described as QGC ports. PX4 normally distinguishes GCS and offboard endpoints; QGC can receive multiple system IDs on its default listening port. Fifty manually configured QGC links are not inherently required. Container-to-host telemetry also needs an explicit reachable destination.

Source: PX4 port documentation
https://docs.px4.io/v1.14/en/simulation/

6. PX4/GAZEBO STARTUP IS INCOMPLETE
---------------------------------

All instances inherit PX4_GZ_STANDALONE=0. The official multi-vehicle example starts the Gazebo server with the first instance and connects later instances using standalone mode. The launcher also gives every PX4 process the same working directory without explicit per-instance storage isolation.

No code arms vehicles or requests OFFBOARD mode. Spawning a model at z=5 is not powered hover.

Source: PX4 multi-vehicle procedure
https://docs.px4.io/main/en/sim_gazebo_gz/multi_vehicle_simulation

7. ROS2 BUILDS AND EXECUTABLE DISCOVERY ARE UNVERIFIED
----------------------------------------------------

Both Python packages lack setup.cfg and explicit ament_python build-type exports. Their installation/discovery needs repair and a real colcon build/ros2 run test. The MAVROS image also lacks the GeographicLib dataset installation normally needed for its geoid conversion.

8. GLOBAL AND VEHICLE-LOCAL COORDINATES ARE CONFLATED
--------------------------------------------------

The same world-grid coordinates are sent directly to MAVROS local-position targets. Each vehicle's local origin can differ. Define and test world ENU, local ENU and PX4 NED transformations before measuring formation error.

9. PX4 V1.14 + HARMONIC IS NOT THE DOCUMENTED BASELINE
----------------------------------------------------

PX4 v1.14 documents Garden support. PX4 v1.16 release notes identify Harmonic as the replacement supported release. Choose a documented compatible combination and pin it; the README currently clones unpinned PX4 main.

Sources:
  v1.14 Gazebo documentation:
  https://docs.px4.io/v1.14/en/sim_gazebo_gz/
  v1.16 release notes:
  https://docs.px4.io/v1.16/en/releases/1.16

10. XRCE-DDS IS ABSENT
---------------------

There is no agent service/process, px4_msgs integration or tested client namespace/key configuration. One shared agent can serve multiple clients; a port per drone is not inherently necessary. Message definitions must match the selected PX4 release.

Source: PX4 XRCE-DDS documentation
https://docs.px4.io/main/en/middleware/uxrce_dds

11. MPS TRAINING MUST MOVE OUT OF THIS LINUX CONTAINER DESIGN
----------------------------------------------------------

PyTorch MPS uses macOS Metal. Ordinary Linux containers on Docker Desktop do not provide that MPS training environment. Run training natively on macOS, or use CPU/Linux CUDA hardware elsewhere. PYTORCH_ENABLE_MPS_FALLBACK=1 does not add Metal access. Docker's other host-assisted inference features do not establish generic PyTorch MPS training support.

Sources:
  PyTorch MPS:
  https://docs.pytorch.org/docs/stable/notes/mps.html
  Docker GPU support:
  https://docs.docker.com/desktop/features/gpu/

12. RESOURCE LIMITS ARE NOT PERFORMANCE EVIDENCE
----------------------------------------------

Compose caps total 13 GiB, but Docker currently has only 7.65 GiB allocated. Neither number establishes actual workload consumption. Leaving only 2 GB for macOS on a 16 GB machine is an aggressive assumption.

RTF must be measured. A controller “20 Hz” in wall time and a simulator running below real time also require an explicit timebase policy.

13. ACCURACY AND ORCA GUARANTEES ARE OVERSTATED
--------------------------------------------

±2 cm needs a defined reference, error statistic, noise model and test duration. Perfect simulated sensors can make it trivial; noisy sensors and wind can make it unattainable.

ORCA provides collision-free conditions under its motion assumptions; it does not automatically guarantee safety for thrust-limited quadrotors in gusts. A 0.25 m collision radius and 0.50 m center spacing leave zero geometric clearance. A 0.30 m emergency threshold would already be inside those collision bodies.

Source: Original ORCA project
https://gamma-web.iacs.umd.edu/ORCA/

14. PBFT SPECIFICATION NEEDS CORRECTION BEFORE IMPLEMENTATION
----------------------------------------------------------

- f=floor((N−1)/3), not generally floor(N/3).
- With 50 voters and f=16, quorums of 33 can intersect in only 16 nodes—all potentially faulty. Use a justified quorum such as 34, or a specified 49-voter configuration.
- Two all-to-all phases cost roughly 4,900 deliveries, plus pre-prepare/client traffic—not approximately 2,500 total. DDS publish calls and network deliveries are different metrics.
- A 2-second failure timeout contradicts end-to-end view change below 200 ms.
- “No proposal for 2 seconds” is not sufficient failure detection during idle periods.
- HMAC uses shared secrets, not a private-key signature scheme; identity/key ownership must be defined.

The 200 ms claim is unverified.

Source: Original PBFT paper
https://www.scs.stanford.edu/nyu/03sp/sched/bfs.pdf

15. OTHER DOCUMENT CORRECTIONS
-----------------------------

- 7×7 has 49 positions. Current vehicle 50 is at (-6,8), forming an extra row.
- The “15-dimensional EKF” listed state actually has 13 components.
- Define the compression of ten neighbor velocities before claiming a 47-dimensional observation.

G. SCOPE DECISION
=================

Your remaining weeks are unknown. The complete original plan is too large to responsibly promise from the current state, particularly if approximately six weeks remain in the intended 16-week schedule.

My recommended defensible project is:

- 5–10 PX4 drones with measured headless Gazebo performance.
- PX4's existing estimator and position controller as the baseline.
- Static formation plus Hungarian assignment.
- One research extension: wind recovery OR communication-loss resilience.
- Repeated experiments, real telemetry and documented limits.

Defer custom EKF, custom MPC, MAPPO, PBFT and simulated FHSS unless the baseline is accepted early. Choose at most one later extension.

If distributed consensus is your main research interest, benchmark PBFT separately with simulated replicas and connect it to low-rate mission commands. If control learning is the main interest, train a small MAPPO environment natively and treat PX4 transfer as a separate validation step.

Keep N=50 as a scaling experiment, not a graduation dependency.
