1. EXECUTIVE SUMMARY

SwarmNet v2.0 is a research-level autonomous drone swarm system simulating
50 quadrotor drones operating with a minimum inter-drone spacing of 50 cm
under adversarial conditions including strong wind (up to 15 m/s) and heavy
electronic jamming.

The system uses a 1-master + 49-follower architecture where Vehicle 1
(master drone) runs the PX4 autopilot stack and an AI-based MAPPO
(Multi-Agent Proximal Policy Optimization) swarm controller. Follower drones
execute decentralized actor policies trained by the master's centralized
critic.

The entire system runs in Docker containers on a MacBook with Apple M4 Pro,
using PX4 SITL (Software In The Loop), Gazebo Harmonic physics simulation,
ROS2 Humble middleware, and QGroundControl as the ground station — the exact
stack visible in the project reference screenshot.

SwarmNet v2.0 is a direct, research-grade successor to SwarmNet v1.0
(Python + ZeroMQ + Raft + Pygame) and represents a complete stack upgrade
to industry-standard autonomous systems tooling.


2. PROBLEM STATEMENT

SwarmNet v1.0 demonstrated distributed consensus (Raft), gossip-based state
sync, and Reynolds flocking in a software simulation. However, it had
fundamental limitations that prevent real-world applicability:

  L1. Scale: v1.0 handled 5–20 nodes. Real operational swarms need 50+.

  L2. Physics fidelity: v1.0 used 2D dot-on-screen simulation with no
      aerodynamic model, no wind, no sensor noise, no actuator delays.

  L3. Safety: v1.0 had no hard collision avoidance. At 50cm spacing with
      real flight dynamics, collisions are a safety-critical problem.

  L4. Adversarial resilience: v1.0 simulated packet loss but had no model
      of GPS spoofing, RF jamming, or sensor corruption.

  L5. Control quality: Reynolds flocking with hand-tuned weights breaks
      down at N=50 in complex, dynamic environments. AI control is needed.

  L6. Standard tooling: v1.0 used custom Python processes. Real drone
      systems use PX4, ROS2, MAVLink, and DDS — which v2.0 implements.

SwarmNet v2.0 addresses all six limitations, producing a simulation system
that is directly transferable to real hardware with minimal changes.

4. GOALS & OBJECTIVES

PRIMARY GOALS

  G1. Deploy and coordinate 50 simulated drone instances (1 master +
      49 followers) in Gazebo Harmonic via PX4 SITL on Docker.

  G2. Maintain 50 cm minimum inter-drone spacing with ±2 cm positional
      accuracy during formation flight, transitions, and hover.

  G3. Sustain stable swarm operation under 15 m/s wind using Extended
      Kalman Filter sensor fusion and Model Predictive Control.

  G4. Maintain swarm cohesion and communication under heavy RF jamming
      using Frequency-Hopping Spread Spectrum simulation and optical
      flow fallback when GPS is spoofed.

  G5. Train and deploy a MAPPO multi-agent reinforcement learning
      controller that outperforms hand-tuned PID/MPC in formation
      accuracy and energy efficiency.

  G6. Demonstrate Byzantine fault tolerance using PBFT consensus for
      critical swarm commands, tolerating up to floor(N/3) malicious nodes.

RESEARCH OBJECTIVES

  O1. Benchmark MAPPO vs MPC vs PID controllers across: formation
      error, energy consumption, recovery time after fault.

  O2. Quantify swarm performance degradation vs wind speed (0–15 m/s)
      and jamming intensity (0–100% channel interference).

  O3. Measure ORCA collision avoidance effectiveness at 50cm spacing
      during formation transitions with 50 agents.

  O4. Compare Raft (v1.0) vs Raft+PBFT hybrid (v2.0) in terms of
      fault coverage, latency overhead, and message complexity.

7. CORE CHALLENGES

CHALLENGE 1 — 50 CM SPACING IN DYNAMIC FLIGHT
  Flying 50 drones within 50 cm of each other is an extreme precision
  requirement. At this spacing, a 10 cm position error in strong wind
  means collision. This requires:
  - Sub-10ms control loop latency
  - EKF sensor fusion (not GPS alone)
  - MPC predictive compensation
  - ORCA hard collision avoidance as safety backstop
  - Hungarian optimal formation assignment

CHALLENGE 2 — HEAVY ELECTRONIC JAMMING
  Electronic jamming in military / contested scenarios disrupts:
  - GPS (position estimate collapses)
  - RF data links (MAVLink / DDS messages drop)
  - Drone-to-drone mesh (gossip/consensus breaks down)
  Solution: FHSS channel hopping, optical flow + IMU dead reckoning,
  PBFT Byzantine consensus to reject spoofed commands, 10-second
  autonomous hold on comms loss.

CHALLENGE 3 — AI CONTROL AT N=50
  Hand-tuned controllers (PID, MPC) require individual tuning per drone
  and degrade with scale. MAPPO (Multi-Agent PPO) learns a shared policy
  that generalizes across all 50 drones and improves with training.
  Training challenge: reward shaping must balance formation accuracy,
  collision avoidance, energy efficiency, and fault recovery
  simultaneously across 50 interacting agents.

CHALLENGE 4 — DOCKER ON APPLE SILICON
  PX4 + Gazebo were built for x86/Linux. Running on ARM64 (M4 Pro)
  via Docker requires: ARM64-native images where available, Rosetta 2
  emulation where not, XQuartz for GUI forwarding, careful port mapping
  for 50 MAVLink streams, and resource allocation tuning for unified
  memory architecture.

8. FEATURES & REQUIREMENTS

8.1 FUNCTIONAL REQUIREMENTS


FR-01  50-DRONE SITL DEPLOYMENT
  System must spawn exactly 50 PX4 SITL instances in Gazebo Harmonic.
  Each instance must have: unique MAV_SYS_ID (1–50), unique UDP port
  (14550–14600), unique Gazebo model instance, independent PX4 log.
  All 50 must be launchable with a single command.
  Vehicle 1 is designated master. Vehicles 2–50 are followers.

FR-02  MASTER DRONE — COMMAND & CONTROL
  Master drone (Vehicle 1) must:
  - Maintain MAVLink v2 link to QGroundControl on UDP 14550
  - Accept mission waypoints from QGroundControl operator
  - Compute swarm formation assignments via Hungarian algorithm
  - Broadcast formation targets to 49 followers via DDS topics
  - Run MAPPO centralized critic during training
  - Detect follower drone failures and trigger re-assignment
  - Maintain Raft leader role for consensus commands

FR-03  FOLLOWER DRONES — AUTONOMOUS EXECUTION
  Each follower drone (Vehicles 2–50) must:
  - Receive formation target from master via DDS
  - Execute MAPPO actor policy: local obs → thrust/yaw command
  - Run EKF: fuse simulated IMU + barometer + optical flow
  - Run MPC position controller: 500ms prediction horizon
  - Run ORCA: enforce 50cm minimum spacing every 20ms
  - Hold last known formation for 10s on comms loss
  - Report state (position, battery, status) via DDS at 10 Hz on
    /swarm/drone_<id>/state (e.g. /swarm/drone_1/state; no numeric tokens)

FR-04  EKF SENSOR FUSION
  Extended Kalman Filter must fuse:
    - IMU: accelerometer + gyroscope at 1000 Hz
    - Barometer: altitude at 50 Hz
    - Optical flow: XY velocity at 30 Hz
    - GPS: position at 10 Hz (degraded/absent under jamming)
  EKF output: position estimate ±2cm under nominal conditions,
  ±10cm under GPS-denied jamming with optical flow active.

FR-05  MPC POSITION CONTROLLER
  Model Predictive Controller must:
  - Predict drone state 500ms ahead using quadrotor dynamics model
  - Compute optimal thrust sequence that minimizes position error
  - Re-solve every 50ms (20 Hz control loop)
  - Pre-compensate for measured wind disturbance from EKF
  - Hand off to ORCA if computed velocity violates spacing constraint

FR-06  ORCA COLLISION AVOIDANCE
  ORCA (Optimal Reciprocal Collision Avoidance) module must:
  - Run every 20ms per drone
  - Read neighbor positions from DDS state topic (10 nearest drones)
  - Compute velocity obstacle set for each neighbor
  - Output a collision-free velocity that minimally deviates from MPC cmd
  - Enforce hard 50cm minimum distance (emergency stop at 30cm)
  - Handle simultaneous avoidance for up to 10 neighbors per drone

FR-07  MAPPO AI CONTROLLER
  Multi-Agent Proximal Policy Optimization system must:
  Training:
  - Observation space per drone: [own pos, own vel, 10 neighbor
    relative positions, 10 neighbor relative velocities, wind estimate,
    target formation position, battery level] = 47-dim vector
  - Action space: [thrust_x, thrust_y, thrust_z, yaw_rate] = 4-dim
  - Reward: formation_accuracy(−) + collision_penalty(−) +
    energy_use(−) + task_completion(+)
  - Centralized critic: receives global state of all 50 drones
  - Decentralized actor: each drone sees only local observation
  - Training runs in Docker AI container using PyTorch + Apple MPS
  Inference:
  - Trained actor weights loaded into each follower ROS2 node
  - Runs at 20 Hz alongside MPC (MAPPO output overrides MPC when
    trained policy is active)
  - Fallback to MPC if MAPPO inference latency > 40ms

FR-08  VON KARMAN WIND MODEL
  Gazebo world must include a Von Kármán turbulence plugin that:
  - Simulates continuous gust wind field across the entire arena
  - Supports wind speeds: 0, 5, 10, 15 m/s (configurable)
  - Applies turbulent fluctuations (±20% of mean speed)
  - Applies wind force to each drone model's aerodynamic surface
  - Wind direction configurable per benchmark run

FR-09  JAMMING SIMULATION
  Communications jamming module must simulate:
  - RF jamming: drops DDS messages at configurable rate (0–100%)
  - GPS spoofing: injects false GPS position offset (0–10m error)
  - RSSI monitoring: detects jamming when RSSI drops below threshold
  - FHSS response: automatically switches DDS domain/port on detection
  - Mesh redundancy: each drone maintains 3 backup comm paths
  - Graceful degradation: swarm holds formation autonomously for 10s

FR-10  PBFT CONSENSUS
  PBFT module must handle critical swarm commands (formation change,
  abort, emergency land) using three-phase commit:
  - Pre-prepare: master broadcasts command + sequence number
  - Prepare: each drone broadcasts prepare to all peers
  - Commit: drone executes command after 2f+1 commits received
  - View change: new master elected on primary failure
  - Tolerates floor(N/3) Byzantine (malicious/faulty) drones
  - Must not be used for high-frequency position updates (too slow)
  - Reserved for: mission commands, formation changes, emergency stops

FR-11  QGC INTEGRATION
  QGroundControl (running natively on macOS) must:
  - Display all 50 vehicle icons on the map view
  - Show Vehicle 1 as master (Home marker, green icon)
  - Accept mission plan upload and transmit to master drone
  - Display telemetry for any selected vehicle
  - Show battery, GPS fix, flight mode for all drones
  - Allow operator emergency land / RTL for any drone

FR-12  RVIZ2 VISUALIZATION
  RViz2 node inside ROS2 container must render:
  - 3D positions of all 50 drones as colored markers
  - Formation target positions as ghost markers
  - Position error vectors (actual vs target)
  - ORCA avoidance vectors (togglable)
  - Wind field arrows (togglable)
  - Color-coded drone status: green=OK, yellow=degraded, red=failed

FR-13  METRICS & BENCHMARKING
  System must log and export:
  - Formation error: RMS distance of each drone from target (per second)
  - Collision events: count of <50cm violations per run
  - MAPPO reward: cumulative reward per episode
  - EKF accuracy: estimated vs ground truth position error
  - Comm reliability: message delivery rate per drone pair
  - Election time: PBFT view-change latency
  - Energy proxy: cumulative thrust magnitude per drone
  All metrics exported to CSV. Matplotlib plots auto-generated.


8.2 NON-FUNCTIONAL REQUIREMENTS

NFR-01  PERFORMANCE
  Formation position error < 5cm RMS at 0 wind, 0 jamming.
  Formation position error < 15cm RMS at 15m/s wind, 0 jamming.
  Formation position error < 25cm RMS at 15m/s wind, 50% jamming.
  ORCA must enforce 50cm spacing with zero violations at 0 wind.
  ORCA must have < 3 violations per 60s run at 15m/s wind.

NFR-02  LATENCY
  DDS state update: drone → master < 3ms on localhost Docker network.
  MAPPO inference: < 40ms per drone per control tick.
  MPC solve time: < 50ms per drone (20 Hz loop).
  ORCA solve time: < 5ms per drone (50 Hz loop).
  PBFT command commit: < 200ms for N=50.

NFR-03  SCALABILITY
  All 50 drones must run simultaneously in Docker on M4 Pro 16GB.
  Total RAM usage must stay below 14GB (leaving 2GB for macOS).
  System architecture must support N up to 100 with config change only.

NFR-04  FAULT TOLERANCE
  PBFT: correct operation with up to floor(50/3) = 16 Byzantine nodes.
  Raft: correct leader election with up to floor(50/2) = 24 crash faults.
  Comms loss: swarm holds formation autonomously for minimum 10 seconds.
  Single drone crash: swarm rebalances formation within 5 seconds.

NFR-05  REPRODUCIBILITY
  All random seeds (wind, spawn positions, jamming) configurable in YAML.
  Docker images pinned to exact versions for reproducible builds.
  All benchmark results reproducible within ±5% given same seed.

NFR-06  PORTABILITY
  Primary: macOS Apple Silicon (M4 Pro) via Docker.
  Secondary: Ubuntu 22.04 x86 (direct install, no Docker needed).
  All Docker images must have ARM64 variants or Rosetta 2 fallback.

NFR-07  SAFETY
  ORCA hard stop at 30cm (below 50cm warning threshold).
  Emergency land command takes priority over all other commands.
  Master drone failure triggers autonomous hover hold on all followers.
  No drone may enter OFFBOARD mode without valid setpoint stream.

13. RISKS & MITIGATIONS

  R1. Docker RAM exhaustion at 50 drones
      Mitigation: Cap each PX4 instance to 200MB via Docker cgroups.
      Test at N=10, 20, 30 first. Scale to 50 only after profiling.

  R2. Gazebo GUI too slow via XQuartz on macOS
      Mitigation: Use headless Gazebo (HEADLESS=1) + RViz2 for all
      visualization. RViz2 runs inside VS Code Remote Container.

  R3. MAPPO training takes too long on M4 Pro CPU
      Mitigation: Use Apple MPS backend in PyTorch 2.x for GPU
      acceleration. Start training with N=10 drones, transfer to N=50.

  R4. PX4 ARM64 image unavailable for some versions
      Mitigation: Use Rosetta 2 emulation in Docker Desktop for
      x86 images. Enable in Docker Settings → Features in development.

  R5. DDS discovery overhead at N=50
      Mitigation: Partition DDS into subgroups. Use ROS_DOMAIN_ID
      segmentation. Reduce discovery beacon frequency in Cyclone config.

  R6. ORCA not fast enough at 20ms for 50 drones
      Mitigation: ORCA is O(N) per drone. At N=50, each drone checks
      10 nearest only (K-D tree neighbor lookup). C++ implementation.

  R7. PBFT latency too high for formation commands
      Mitigation: PBFT only used for mission-critical commands
      (< 1 per second). Position updates go via DDS directly.
